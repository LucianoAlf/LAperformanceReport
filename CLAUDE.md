## Stack

- **Frontend:** React 19 + TypeScript 5.8 + Vite 6 (porta 5175)
- **Styling:** Tailwind CSS (dark mode via `class`) + Radix UI + Lucide icons + CVA
- **Backend:** Supabase (PostgreSQL + Auth + RLS + Storage + RPC)
- **IA:** OpenAI API (assistente com function calling)
- **Automação:** n8n (webhooks)
- **Routing:** React Router 7 (lazy loading por rota)
- **Forms:** React Hook Form + Zod
- **Charts:** Recharts
- **Datas:** date-fns

- **`movimentacoes_admin.emusys_matricula_id`** (2026-07-02): coluna nullable/forward-only usada p/ **deduplicar renovações** reenviadas pelo Emusys. O Emusys reenvia o webhook `matricula_renovacao` inteiro a cada edição de cronograma; a `competencia` é calculada e muda entre entregas (antecipada↔normal), então NÃO serve de chave de dedup. `matricula_id` é estável → dedup na edge por `emusys_matricula_id` (janela 60 dias), mantendo o check antigo (aluno+curso+competência) como rede. Seguro p/ multi-curso (cada curso = matricula_id próprio). Ver `docs/superpowers/plans/2026-07-02-dedup-renovacao-matricula-id.md`.
- **`movimentacoes_admin` não aceita mais DELETE de usuário (2026-08-10).** Trigger `trg_bloqueia_delete_movimentacao_admin` recusa DELETE quando há JWT na sessão; o caminho é a RPC **`arquivar_movimentacao_admin(id, motivo)`**, que move a linha para `movimentacoes_admin_arquivadas` com autor/data/motivo. `service_role` segue livre — a edge precisa apagar aviso prévio removido na fonte. **Por que lixeira e não soft delete:** `anulado` existe e é respeitado por `movimentacoes_admin_vigentes`, mas **25 funções vivas ainda leem a tabela crua** — marcar `anulado` nelas não surtiria efeito, e migrar as 25 é risco desproporcional; mover a linha a some das 25 de uma vez (mesmo padrão de `alunos_arquivados`). Os dois mecanismos coexistem com sentidos distintos: **anulado** = "existe mas não conta" (duplicata de renovação, rastro visível); **arquivado** = "não deveria existir". ⚠️ Motivo do bloqueio: em 03/08/2026 a ADM do Recreio deletou a renovação da Catarina Petrolongo (`audit_log` registro 3178) — via duas linhas da mesma aluna e **a tela só oferecia excluir**. Apagou justamente a do webhook, a única com a data da 1ª aula, e o snapshot de julho ficou apontando para um registro inexistente. Detecção contínua em **`vw_renovacoes_duplicadas_suspeitas`** (já desconta anuladas desde `20260810172458`; é SUSPEITA, não veredito — o padrão `valor_congelado` tem falso positivo por construção).
- **Competência da renovação = mês da 1ª AULA do novo ciclo (regra confirmada pelo Alf, 2026-08-10).** Não é o mês em que a equipe negociou, nem o mês em que o contrato passa a faturar. ⚠️ **Havia duas fontes de escrita com regras diferentes para o mesmo campo**, e era a causa-raiz das duplicatas de renovação: o webhook (`processar-matricula-emusys`) usa `inicioMesISO(dataPrimeiraAulaNovoCiclo || dataMovimento)` ✅, mas o `FormRenovacao` calcula pelo mês da `data_renovacao` ❌ — e o lançamento manual **não tem** a data da 1ª aula. Resultado: a equipe lançava à mão ao negociar, o Emusys mandava o webhook dias depois com a data real, e nasciam **duas linhas com competências diferentes** (medido: 4 casos só no Recreio/jul-2026 — lote manual de 03/07 com 1ª aula real em 03/08, 05/08 e 10/08). A edge agora **reconcilia em vez de ignorar**: ao achar um lançamento adiantado sem 1ª aula, completa a data, recalcula a competência e faz backfill do `emusys_matricula_id` (v81). Tem rede para o órfão **sem vínculo** (mesmo aluno+unidade+**curso**, sem 1ª aula, 60 dias) — sem ela a busca por `emusys_matricula_id` não alcança justamente o registro manual, que é o problema. ⚠️ O `FormRenovacao` **continua gravando a competência pelo mês do lançamento**: quem nunca receber webhook do Emusys fica errado (72 órfãos em 60 dias, 61 deles no Recreio). ⚠️ **O recesso escolar desloca a competência de propósito** — a 1ª aula pós-recesso 19/07–01/08 caiu em agosto, então quem renovou em julho conta em agosto. É esperado, não erro.
- **Renovação duplicada: a prova está no CONTRATO, não no valor (2026-08-10).** O Emusys **abre um `contrato_id` novo a cada renovação**, e as parcelas seguintes apontam para ele — contar, **por matrícula**, os contratos que estreiam no ano dá o número real de renovações. Contar por *aluno* erra: Pérola Madeira tinha 2 registros no mesmo mês, mesmo curso e mesmo valor (a cara de uma duplicata) e eram as matrículas **519 e 520** renovando juntas. ⚠️ O critério por **valor da parcela** parece equivalente e não é: renovação sem reajuste não gera degrau (417→417), juros/multa inflam o `valor_pago` criando degrau falso (367→456,61 era juros), e parcela dividida vira duas linhas na mesma competência (406 + 54). ⚠️ **`valor_original` é valor de TABELA** (todo CG = 447) — só o líquido (`− desconto_fixo − desconto_condicional`) reflete o contratado. Bolsista (mensalidade 0 ou 15) não emite parcela, então nenhum dos dois critérios o alcança. Registro duplicado é **anulado, nunca deletado** (`movimentacoes_admin.anulado`); a leitura canônica é a view `movimentacoes_admin_vigentes`. Método e evidência aluno a aluno: `docs/auditorias/2026-08-10-duplicatas-renovacao-por-contrato.md`.

Descartados antes, todos derivados de contagem: `turma_nome` (preenchido em 171 das 179 "individual" — é o nome do slot), `qtd_alunos` do container (**sempre** igual ao nº de contratos) e `cursos.natureza_operacional`/`capacidade_maxima` (pedagógica/comercial e NULL em todos).
- **Filtro é de LOTAÇÃO, não de modalidade.** Como a modalidade é "turma" em 99%, filtrar por ela devolveria quase tudo ou quase nada. O segmented virou **Sozinho | Com turma** (`FiltrosAgenda.lotacao`, lê `qtd_alunos`); a modalidade continua visível no painel de detalhe. Aula com 0 alunos vinculados **não** é "sozinho" — é vínculo faltando, outro problema.
- **Filtros e período:** busca livre (aluno/professor/turma/sala, sem acento), selects de professor/curso/turma, segmented de lotação (Sozinho|Com turma) e ocultar canceladas — tudo no cliente, sobre o que a RPC já devolve. O período usa o `CompetenciaFilter` compartilhado e sincroniza nos **dois sentidos**: trocar o período salta para dentro dele, e navegar para fora reposiciona o período no mês do dia. Sem isso o topo dizia "Jul/2026" com agosto na tela.
- **Aluno preso na turma antiga — reconciliação por webhook (v2, 2026-08-15).** Quando o aluno troca de turma/curso, a aula antiga **continua existindo no Emusys**; ela só deixa de vir na consulta dele. O que fica errado do nosso lado é o **vínculo** (`aula_alunos_emusys`), não a aula — e como a Agenda lê essa tabela, o aluno aparece numa turma que não é mais dele. O webhook **`matricula_alterada`** dispara a edge **`reconciliar-grade-aluno`** (`verify_jwt=false`, bearer em tempo constante), que lê `GET /aulas?pessoa_id=` **paginado** e chama a RPC **`reconciliar_grade_aluno_v2`**, que faz `delete from aula_alunos_emusys` **apenas da linha daquele aluno**. 4 guardas: foto vazia aborta, janela limitada a ontem+ (⚠️ é `< hoje - 1`, não `< hoje` — a edge manda `dataInicio = ontem` e `< hoje` abortaria 100% das chamadas), slot parcialmente vivo preserva (o Emusys entrega o mesmo horário em 2 linhas, `turma`+`individual`) e **presença lançada por humano preserva** (`aluno_presenca.respondido_por` do PRÓPRIO aluno). Aplicado em 15/08: **32 vínculos removidos, 0 aulas canceladas**. ⚠️ **A v1 CANCELAVA A AULA e estava errada** — `p_ids_vivos` vem de `pessoa_id`, que responde "as aulas DO ALUNO", não "as aulas que existem"; cancelar tiraria a aula dos colegas (uma das turmas tinha 6 alunos). Provado na API por janela de DATA e na tela: as 4 aulas do aluno 1452 que a v1 cancelaria seguem `cancelada=false` com `alunos=0`. **Aula vazia é comportamento normal do Emusys** (3 das 126 aulas do Recreio em 17/08, 2,4%). A v1 foi dropada. ⚠️ **Ela nunca funcionou**: gravava `cancelada_origem='sync_ausente_emusys'` numa coluna cuja CHECK só aceitava `('emusys','agenda_secretaria')`, todo cancelamento estourava e o try/catch do webhook engolia — validada em **dry-run**, que não escreve e por isso não pegou. ⚠️ **Reagendamento não passa por aqui e nem precisa**: preserva o `emusys_id` e o upsert move a linha (357 reagendamentos, zero duplicata). ⚠️ O cenário em que o Emusys de fato **apaga** a aula (alteração da data da 1ª aula, `data_primeira_aula` é parâmetro do contrato) **não foi observado nenhuma vez** em 4 dias de webhooks reais — segue coberto pelo soft-cancel diário do `sync-grade-futura-emusys`. ⚠️ Ao cruzar com a API use **`emusys_id`**; `aulas_emusys.id` é chave local. ⚠️ Escopo é só o futuro (decisão do Hugo); o backlog não foi limpo.
- ⚠️ **`professor_presenca` é `'ausente'` por DEFAULT no Emusys** — 100% das aulas *futuras* vêm assim sem ninguém ter faltado (medido: 10.522 futuras, todas 'ausente'). Só exibir depois que a aula terminou (`aulaJaOcorreu`), senão a tela acusa falta de metade do corpo docente todo dia.
- **Decisão humana em `aulas_emusys` é protegida por trigger, não por trava na edge (2026-08-12).** `professor_presenca` é escrita por **quatro** caminhos (`sync-presenca-emusys` nos modos `presenca`/`agenda`/`metadados` + `sync-grade-futura-emusys`), e o modo `metadados` roda **a cada 15 min** cobrindo ontem→+14 dias — como o Emusys manda `'ausente'` por default em aula que não ocorreu, a marcação da secretaria durava um ciclo de cron. Medido em 12/08: **77 de 83 marcações (92,8%) revertidas**. Corrigido com a coluna **`professor_presenca_origem`** (espelha `cancelada_origem`) + trigger **`trg_proteger_decisao_humana_aula`**, que devolve o valor humano em qualquer UPDATE que não declare `set_config('app.escrita_humana_aula','on',true)` — flag que só as RPCs `app_{registrar,remover}_presenca_professor_dia` e `app_marcar_presenca_professor_aula` setam. ⚠️ **A discriminação é por flag de transação, não por conteúdo do UPDATE**: sem ela, a própria secretaria ficaria impedida de corrigir a marcação (presente→ausente seria lido como sobrescrita). ⚠️ **Por que trigger e não trava na edge:** o padrão da edge (`cancelamentosHumanos`) cobre só `sync-presenca-emusys` — `sync-grade-futura-emusys:171` grava `cancelada` **sem** ele, deixando o cancelamento humano com furo latente (não exercitado: zero linhas com `cancelada_origem`). O mesmo trigger fecha esse furo. É o padrão de `trg_proteger_anotacoes_fabio`, que já protegia `anotacoes_fabio` na mesma tabela pelo mesmo motivo. ⚠️ `'ausente'` **com** origem preenchida é decisão humana e fica protegido — é o que distingue "a secretaria marcou ausente" de "o Emusys ainda não lançou".
- ⚠️ **`app_{registrar,remover}_presenca_professor_dia` filtram `categoria='normal'`** — aula `extra` e `experimental` **nunca** é marcada pelo botão do dia e fica com o default `'ausente'` do Emusys. Bug conhecido, não corrigido em 12/08.
- **Cache + prefetch:** o hook guarda os dias já vistos (chave `unidade|data`) e adianta os vizinhos 300 ms após a carga. Revalida sempre em segundo plano — cache serve só para pintar na hora.
- ⚠️ **`aula_alunos_emusys` é a tabela CANÔNICA do vínculo aula↔aluno**, com 18 RPCs consumindo (LA Teacher, presença, health score, carteira). Não criar tabela paralela — foi tentado e revertido durante a implementação deste módulo (ver `.claude/memory/integracao-infra.md`).
- ⚠️ **RLS de `aula_alunos_emusys` (02/08/2026):** `get_agenda_dia` é **SECURITY INVOKER**, então quem chama precisa de acesso próprio à tabela. Ela só tinha policy `TO service_role` e nenhum `GRANT SELECT` p/ `authenticated` — a tela quebrava com `permission denied` para 100% dos usuários e o bug atravessou 14 tasks porque **toda validação foi feita como `service_role`, que ignora RLS**. Hoje tem `GRANT SELECT` + policy `aula_alunos_emusys_leitura_escopada` (`is_admin() OR unidade_id IN (get_user_unidade_ids()) OR professor da aula`, mesma forma de `aluno_presenca`). **Regra geral:** validar RPC SECURITY INVOKER sempre com `set local role authenticated` + `set local request.jwt.claims` de um usuário real; `GRANT` sem policy é pior que o erro (lê zero linhas e falha em silêncio).
- **Visão consolidada:** com `unidadeSelecionada = null`, a unidade entra no rótulo do trilho e no drawer — e na **chave do agrupamento**. Sem isso, "Sala 1" das três unidades vira um trilho só com as aulas sobrepostas.
- **Linguagem visual (03/08/2026): cor é vocabulário de EXCEÇÃO.** A aula normal — esmagadora maioria — ficava com borda esmeralda; quando tudo está destacado, nada está. Hoje ela é neutra, e a borda esquerda colorida marca só o que exige olhar: acontecendo agora (emerald), experimental (violet), reagendada (amber), cancelada (rose), sem aluno (tracejado). ⚠️ O estado é **um único valor** (`estadoDaAula` em `AgendaCard.tsx`), nunca condições independentes — `cn()` usa twMerge e a última classe conflitante vence, o que já produziu bug real aqui. As marcas `E`/`✕`/`R`/`!` viraram **pontos** (âmbar = risco ≥ 40%, rose = inadimplente), **estrela** (aluno novo) e contador de turma, com **legenda permanente** no rodapé da grade — sinal sem legenda visível é enigma. A legenda fica FORA do bloco rolável (senão as gridlines a cruzam).
- **Leitura do dia:** véu sobre as horas já vencidas + hora corrente destacada, além da régua de segundos. O rótulo do trilho deixou de repetir "N aulas" e passou a carregar iniciais (`iniciaisDoNome` — primeiro + **último** nome, senão "Ana Maria Ribeiro" e "Ana Maria Souza" colidiriam em `AM`), curso predominante (`cursoPredominante`, só ao agrupar por professor — numa sala não diz nada), aulas vivas e barra de ocupação (`ocupacaoPct`, **união** de intervalos e não soma: duas aulas sobrepostas de 1h ocupam 1h, não 2). Sobreposição ganha etiqueta âmbar no rótulo (`resumoSobreposicao`) — o empilhamento em faixas já existia, mas só deixava o trilho mais alto, e ninguém repara nisso varrendo a grade. Não vai no card: as bordas já carregam estado e dois códigos de cor no mesmo lugar se anulam.
- **Barra de comando única + popover de filtros:** navegação do dia, agrupamento e busca ficam à vista; professor/curso/turma/categoria/modalidade e "ocultar canceladas" vão para o popover, com badge de quantos estão ligados (`contarFiltrosAvancados` — a busca não conta, está visível). O `CompetenciaFilter` compartilhado segue como faixa própria, **intocado**.
- **Painel sob demanda:** o `AgendaDrawer` só é montado com aula selecionada — antes ocupava 296 px permanentes para dizer "selecione uma aula". Numa grade que rola na horizontal, largura é o recurso escasso: devolver esses 296 px é o que mais empurra o ponto de rolagem para longe. Fecha no botão ou no `Esc`.
- **Cartão mantém a duração real** (decisão Hugo, 03/08/2026). Encaixá-lo na célula da hora alinharia tudo à gridline, mas apagaria a folga de 10 min entre aulas — e é ela que vira horário livre quando a disponibilidade entrar.
- **Pendência consciente:** o filtro "Todos | Com aula" do spec não foi implementado — "Todos" exigiria uma lista de professores/salas independente das aulas, que a RPC não devolve.
- **Design system nos filtros (03/08/2026):** os `<select>` nativos do popover saíram. Professor/Curso/Turma viraram **combobox com busca** (`Command` + `Popover`, mesmo padrão de `combobox-nome`); Categoria continua `Select` (5 valores fixos com contagem — caixa de busca ali é ruído). ⚠️ **O Radix proíbe `value=""`** (string vazia é reservada e ele lança exceção), e era a sentinela de "sem filtro" dos `<option>` — virou o token `SEM_FILTRO`. ⚠️ **Dropdown do Radix é portalado para o `<body>`**, fora do popover de filtros: sem a guarda `PORTAL_FLUTUANTE` no handler de `mousedown`/`Esc`, escolher uma opção contaria como "clique fora" e fecharia o popover no mesmo gesto.
- **Seletor de período próprio** (`SeletorPeriodo.tsx`, 03/08/2026): painel de duas colunas — escopo à esquerda por extenso, grade contextual à direita (12 meses / 4 trimestres / 2 semestres / anos), rodapé com o intervalo escrito por extenso ("T3" não diz quais meses entram). ⚠️ **Substitui a APRESENTAÇÃO, não o estado**: dirige as mesmas funções de `useCompetenciaFiltro`, então o período continua sendo o objeto que o `AppLayout` distribui — inclusive ao chegar de outra tela com período já escolhido (por isso `Hoje`/`Tudo` seguem no trilho, senão o painel abriria sem nada marcado). O `CompetenciaFilter` compartilhado **não foi tocado** e segue nas páginas irmãs. Clicar num **valor** aplica e fecha; trocar de **escopo** não fecha.
- **Topo em uma faixa só:** competência e comandos do dia dividem a mesma linha (eram duas, ~90px antes da grade começar). O rótulo perdeu o "-feira" e o ano ficou apagado.
- **Sobra de altura vira card maior, não grade vazia** (decisão Hugo): as faixas são resolvidas antes da altura e a sobra é distribuída resolvendo `alturaMinima = fixo + nFaixas × altura`. O cabeçalho das horas é **medido** (erro ali multiplica pelo nº de trilhos). Teto `AGENDA_ALTURA_FAIXA_MAX_PX = 96` — sem ele, um dia com um professor viraria um retângulo de meia tela. Card alto passa a mostrar a 3ª linha, igual card largo. ⚠️ O `minHeight` vai no bloco **interno** da timeline, não no container rolável: gridlines, véu e régua são `absolute top-0 bottom-0` dele. É `minHeight` e não `height` para a consolidada (40+ professores) continuar rolando pelo conteúdo.
- **Tooltip de resumo no hover do card** (`ResumoDaAula`): cobre o mesmo conjunto do tooltip do Emusys (turma, curso, horário, duração, sala, nr da aula, modalidade, nº de alunos, inadimplência) e acrescenta nome **inteiro** de cada aluno, risco, aluno novo, presença e as anotações (`anotacoes` do Emusys, em ~19% das aulas; `anotacoes_fabio` do LA Teacher). Os `title` nativos saíram — abririam o tooltip do SO por cima. ⚠️ **Presença só depois de `jaOcorreu`** (mesmo portão do drawer): além do `professor_presenca` vir `'ausente'` por default em 100% das futuras, foram medidas 6 linhas de aula futura já marcadas como 'falta' em `aluno_presenca`. ⚠️ **A presença chega pelo sync, não ao vivo** — dias passados têm 85-95% de cobertura, mas o próprio dia tinha 2,7% em 03/08; por isso aula terminada sem presença mostra "Presença ainda não sincronizada" em vez de sumir em silêncio. ⚠️ **Não dizemos "N faturas atrasadas"** como o Emusys: só existe o booleano `inadimplente` por aluno, nunca a contagem — o texto fala de alunos.

## Regras Importantes

- **Timezone:** BRT (UTC-3) — sempre usar offset ao trabalhar com datas do negócio
- **Banco:** todas operações passam pelo client em `src/lib/supabase.ts`
- **Estado:** não usar Redux ou state managers externos — preferir hooks + Context
- **Hooks:** preferir hooks customizados para lógica de negócio reutilizável
- **MCP (OBRIGATÓRIO):** Sempre utilize ferramentas MCP proativamente para análise e investigação. Antes de explorar código manualmente, verifique se há um MCP disponível que facilite a tarefa (ex: Supabase MCP para consultar banco, n8n MCP para verificar workflows, NocoDB MCP para dados). MCPs são a via preferencial para acessar dados reais do sistema — use-os ANTES de ler código fonte quando precisar entender estado atual do banco, schemas, dados ou configurações.
- **Ler a fonte antes de afirmar (OBRIGATÓRIO):** ao descrever como QUALQUER automação/fluxo funciona (webhook, endpoint Emusys, edge function, workflow n8n, trigger, RPC), é proibido afirmar de memória ou por inferência do nome. SEMPRE abrir a fonte primeiro — `n8n_get_workflow` (mode full/structure), o código da edge, a definição da função no banco. Frases como "X não é usado", "Y é só manual", "Z não chama o Emusys" exigem verificação na fonte antes de serem ditas. As memórias podem estar desatualizadas (ex: o NocoDB já foi documentado como ativo quando não era mais) — memória é pista, não prova. Mapa canônico do ciclo Emusys: `docs/MAPA-INTEGRACAO-EMUSYS.md`.
- **Memória Self-Heal:** manter arquivos em `.claude/memory/` atualizados proativamente. Ao descobrir regras de negócio, padrões de código ou mudanças no domínio, atualizar o arquivo de memória correspondente e informar o usuário. Ver protocolo completo em `MEMORY.md`.
- **DRY antes de criar (OBRIGATÓRIO):** antes de propor view/tabela/RPC/hook/componente novo, procurar se já existe algo que resolve total ou parcialmente (`docs/MAPA-SISTEMA.md`, `graphify affected`/`explain`, `list_tables` do MCP Supabase). Preferir **estender** o que existe a duplicar. Caso real: "Contratos Vencendo" (28/07/2026) nasceu desenhada com edge function nova, cron novo, tabela nova, cache no cliente e ~218 chamadas/dia à API do Emusys — investigando o banco, `vw_jornada_aluno_atual` já entregava os mesmos 16 alunos (aluno, curso, professor, última aula, aulas restantes), e o vencimento da fatura era derivável de campos que o sync já buscava. Resultado: a feature virou 1 view SQL + 4 colunas aditivas. Quando estender for arriscado (objeto com consumidor ativo em produção), dizer isso explicitamente e decidir conscientemente entre estender com cautela ou duplicar — não estender às cegas. Repetiu no módulo Agenda (02/08/2026): `aula_alunos` nasceu duplicando `aula_alunos_emusys` (18 RPCs consumindo) — descartada, estendeu-se a tabela existente.
- **Deploy de edge via MCP reseta `verify_jwt` para `true` (OBRIGATÓRIO conferir):** `deploy_edge_function` tem esse default e NÃO lê o `supabase/config.toml`. Isso já derrubou `sync-inadimplencia-emusys` e, em 02/08/2026, `sync-presenca-emusys` (401 no gateway antes do código rodar, cron de 15 min quebrado por horas) — o `pg_cron` marca `succeeded` mesmo assim, pois só avalia se o `net.http_post` foi enfileirado. Sempre passar `verify_jwt` explícito conferido contra o `config.toml`, e depois do deploy verificar que o cron respondeu 200 — não só que a função subiu.
- **RLS: chamada de função solta na policy roda UMA VEZ POR LINHA.** `is_admin()`, `auth.uid()`, `auth.role()`, `fn_professor_do_usuario()` — se não estiverem dentro de `(select …)`, o Postgres não consegue tratá-las como constantes e as reavalia a cada linha avaliada. Envolver em `(select fn())` vira `InitPlan`, avaliado uma vez por query, com **semântica idêntica**. Medido em 02/08/2026: `get_agenda_dia` caiu de **1175 ms → 95 ms**; `aula_alunos_emusys` de **341 ms → 6,7 ms**; `alunos` de 33 → 2,2 ms. ⚠️ **Não envolver** expressão correlacionada com a linha (`unidade_id = x`, `EXISTS (… where u.aluno_id = alunos.id)`) — só a chamada de função. Corrigidas as 5 policies do caminho da Agenda (migration `20260802145546_rls_initplan_caminho_agenda`) e, em 04/08/2026, o caminho de leitura de `leads` + 20 policies de SELECT/ALL (migrations `20260804224900_rls_initplan_leads` e `20260804225056_rls_initplan_lote2_leitura`): `leads` caiu de **152,9 ms / 18.849 buffers → 7,5 ms / 1.122**, `renovacoes_legado` 30→1 ms, `crm_lead_historico` 27→9 ms. Ao aplicar, provar equivalência rodando `count(*)` antes/depois com `set local role authenticated` + JWT real de admin, unidade E professor.
  - ⚠️ **MEDIR ANTES DE APLICAR — o advisor não é o mapa.** (a) O advisor `auth_rls_initplan` só detecta `auth.*()`/`current_setting()`, **não** `is_admin()` — por isso `leads`, o maior ganho de todos, não aparecia nos 100 avisos. (b) A recíproca também vale: `turmas_explicitas` parecia alvo (dois `EXISTS`, um correlacionado) mas já custa **0,45 ms / 15 buffers** — o planner hasheia sozinho; mexer seria risco sem ganho. (c) `cursos` e `usuarios` têm policy `true`: seus 23M e 219M seq scans **não** vêm da própria policy, e sim de `is_admin()`/`get_user_unidade_id()` chamadas pelas policies de outras tabelas (são PL/pgSQL, que o planner não inlineia). Sempre `EXPLAIN (ANALYZE, BUFFERS)` como `authenticated` antes de decidir.
  - ⚠️ **RLS não alcança RPC `SECURITY DEFINER`** — e quase toda RPC de KPI é. Confirmado medindo `get_kpis_comercial_canonicos_v2` antes/depois: buffers idênticos (~7.460). Esta correção acelera as leituras diretas do PostgREST (`supabase.from(…)`, 235 no `src/`), **não** as RPCs (`supabase.rpc(…)`, 128). Para RPC lenta, o caminho é outro (ver `get_kpis_alunos_canonicos` em `docs/`).
- **`ALTER DEFAULT PRIVILEGES` também pega VIEW, não só função.** Toda relação nova em `public` nasce com `authenticated=arwdDxtm` (todos os privilégios); `grant select` depois **não** tira o resto. Pegou `vw_disciplinas_modalidade` em 03/08/2026, e ali era grave: view simples (SELECT de uma tabela, sem join nem agregação) é **auto-atualizável**, e com `security_invoker = false` a escrita executa com os direitos do **dono** — qualquer usuário autenticado poderia INSERT/UPDATE/DELETE em `emusys_disciplinas_catalogo`, que tem RLS sem policy justamente para ninguém escrever. Ao criar view: `revoke all ... from public, anon, authenticated` **e depois** `grant select`. Conferir em `pg_class.relacl` — o correto para view de leitura é `authenticated=r`.
- **Adicionar JOIN em RPC `SECURITY INVOKER` exige que o USUÁRIO tenha acesso à tabela nova.** Quebrou a Agenda em 03/08/2026 (`permission denied for table emusys_disciplinas_catalogo`, 100% dos usuários) — mesma armadilha do `aula_alunos_emusys` em 02/08, repetida porque a validação foi feita como `service_role`, que ignora RLS. Quando a tabela é trancada de propósito (RLS ligado + zero policies), a saída é **não destrancá-la**: expor só o necessário numa view com `security_invoker = false` (ver regra acima sobre a ACL dela). Validar sempre com `set local role authenticated` nos três perfis.
- **Recriar função (DROP+CREATE) reabre EXECUTE para `anon`.** O projeto tem `ALTER DEFAULT PRIVILEGES` no schema `public` concedendo EXECUTE em funções novas a `anon` — então `revoke … from public` **não basta**, precisa de `revoke execute … from anon` nominal. Pegou `get_agenda_dia` em 02/08/2026, **de novo `get_kpis_alunos_canonicos_base_v131` em 04/08/2026**, e **de novo `aplicar_retificacao_relatorio_gerencial_retencao_v1` em 10/08/2026** (3ª vez) — que é `SECURITY DEFINER`, então ficou executável por `anon`. Sempre conferir `select proacl from pg_proc where proname='…'` depois de recriar; a ACL correta para RPC de app é `{postgres=X, authenticated=X, service_role=X}`. ⚠️ **`CREATE OR REPLACE` com lista de PARÂMETROS diferente não substitui — cria um overload novo** e deixa a versão antiga órfã (drope-a explicitamente).
  - ⚠️ **E se o parâmetro novo tiver `DEFAULT`, o órfão não fica só inerte: ele QUEBRA quem chamava a função.** Com `DEFAULT`, a assinatura nova também aceita a lista de argumentos antiga, as duas viram candidatas e o Postgres recusa: `function … is not unique` (`Could not choose a best candidate function`). Caso real em 11/08/2026: `upsert_lead` ganhou `p_data_nascimento date DEFAULT NULL` e o webhook de leads do Emusys (n8n `EB0LibpOJCLhKp7M`, que chama com 10 args) falhou em **100% das execuções por 21h — 22 leads perdidos**, mais o `agente-webhook` das campanhas, que chama a mesma RPC e **não checa o `error`**, parando de criar lead no funil em silêncio. **Ao acrescentar parâmetro a uma RPC com consumidor externo (n8n, edge, PostgREST), dropar a assinatura antiga no MESMO commit** — e conferir `select oid::regprocedure from pg_proc where proname='…'` depois, que deve devolver UMA linha. Post-mortem: `daily-notes/2026-08-12.md`.
  - ⚠️ **Chamada por PostgREST com chaves NOMEADAS (`supabase.rpc`) não sofre a ambiguidade** — resolve pela lista de nomes. Por isso o incidente derrubou só o n8n (SQL posicional) e não o observador, que chama a mesma função com as 11 chaves. Ou seja: **o teste pelo front/edge passa e o webhook quebra** — validar a forma que o consumidor real usa, não só a sua.
- **Retificação mensal (`fechamento_mensal_retificacoes`): encadear, nunca partir do payload original, quando o snapshot já tem outra correção.** O leitor sempre pega a retificação **mais recente** por `created_at` (não faz merge de várias). Uma segunda função de retificação que monta `v_payload_corrigido` a partir de `v_snapshot.payload` (puro) em vez do `payload_corrigido` da retificação já existente **apaga silenciosamente a correção anterior** — a mais nova vence sozinha. Toda função nova de retificação sobre um snapshot que pode já ter outra: `select … from fechamento_mensal_retificacoes where snapshot_id=… and base_payload_hash=… order by created_at desc limit 1`, e usar `coalesce(payload_corrigido, snapshot.payload)` como base. Caso real (10/08/2026): a retificação de renovações do bloco gerencial (`aplicar_retificacao_relatorio_gerencial_retencao_v1`) roda sobre o **mesmo snapshot** que já tinha a retificação de financeiro (`aplicar_retificacao_relatorio_gerencial_financeiro_v1`, 08/08) — sem encadear, teria revertido o financeiro. Guarda de escopo (`RETIFICACAO_..._ESCOPO_EXCEDIDO`) que recalcula campos vizinhos e aborta se algo alheio mudou é o padrão pra pegar isso — mas é só um sinal de alerta, não limite de escrita: confira o que a função de fato `jsonb_set` antes de decidir se dá pra confirmar e seguir (parâmetro `p_confirma_*`) em vez de reescrever a guarda pra sumir com o aviso.
- **RPC de KPI lenta: procure trabalho DUPLICADO antes de otimizar query.** `get_kpis_alunos_canonicos` levava 7.495 ms / 2.653.236 buffers porque `get_kpis_alunos_admin_operacional` (3.900 ms / 1.310.073 buffers) era chamada **duas vezes** com os mesmos argumentos — uma dentro de `get_kpis_alunos_canonicos_base_v131`, outra no wrapper de topo. Corrigido em 04/08/2026 (`20260804230945`): o topo calcula uma vez e repassa via `p_admin jsonb`. **7.495 → 3.966 ms**, com md5 do jsonb idêntico em 8 cenários. A conta de buffers denuncia esse tipo de caso: se `buffers(topo) ≈ buffers(a) + buffers(b)`, há repetição. ⚠️ Ao mexer em função grande, **não transcreva o corpo à mão** — leia `pg_get_functiondef()`, faça `replace()` com guarda (`raise exception` se o trecho não bater) e `execute`. ⚠️ O que ainda sobra ali são dois `LEFT JOIN LATERAL` com `OR` no predicado (`emusys_matriculas_estado_atual` e `aluno_jornada_matricula_disciplina`) que impedem uso de índice; reescrevê-los é o próximo ganho (~3,9 s → ~1 s), mas mexe no desempate que define a `pessoa_key` e **pode mudar contagem de aluno** — exige validação aluno a aluno, não só de totais.

A aritmética denunciou antes de ler o código: detalhe 86.964 buffers + carteira 87.244 ≈ **172.323 do topo**. Corrigido em `20260808213000` lendo a base uma vez e derivando dela o agregado e as turmas unitárias: **1.626 → 299 ms**, 172.323 → 88.869 buffers (trimestral: 1.114 → 564 ms). Eram ~172k buffers (405k no trimestral) para devolver 74 linhas — só rápido porque tudo estava em `shared_buffers`. O `57014` aparecia quando o cache esfriava ou havia concorrência, e a aba de Professores dispara esta RPC **e** `get_kpis_professor_periodo_canonico_v3` em paralelo. **Quando o tempo está bom mas os buffers são absurdos para o nº de linhas, o problema já existe — só ainda não apareceu.**

Ao decompor pai×filhos, aquecer os filhos primeiro **na mesma transação** — senão a conta de tempo não fecha e se persegue fantasma. A conta de **buffers**, essa, é estável e foi a que apontou a duplicação real da Média/Turma.

OVER (PARTITION BY ap.aula_emusys_id)`): window é **barreira de otimização**, então o `data_aula BETWEEN` da função **não desce** para dentro da view — ela varre e ordena as **50.905** linhas de `aluno_presenca` (+ `aulas_emusys` inteira) e só então descarta **49.053 (96,4%)** pelo filtro de data. ⚠️ **O spill de 4,7 MB NÃO custa tempo**: com `work_mem=24MB` o `temp read/written` some e o tempo fica **224 ms** contra 222 — o SO já absorvia no cache de página. Não subir `work_mem` por isso. O único ganho real (~200 ms) exigiria empurrar o recorte de data para dentro da view, que tem **13 consumidores**, incluindo o Health Score V3 (guardrail: fórmula não muda). Desproporcional para uma RPC que roda em 704 ms contra `statement_timeout` de 8 s. Se um dia virar necessário, o caminho seguro é uma função nova parametrizada por período — não alterar a view compartilhada. A partição é por `aula_emusys_id` e uma aula tem uma data só, então filtrar por data antes da window é semanticamente seguro; falta só provar que não há `aula_emusys_id` com duas `data_aula`.

## Governança de branch (OBRIGATÓRIO — ler antes do primeiro commit)

**Frente encerrada = merge feito.** Não existe "commitei e deixei o PR aberto para depois".
PR aberto com código já aplicado em produção é risco ativo: o banco fica corrigido e a
`main` fica com o código antigo, então qualquer deploy a partir dela **reverte a correção
sem ninguém perceber** — e o sintoma some, porque o dado continua certo. Aconteceu em
2026-08-08 com o PR #75 (faturamento realizado).

Checklist, na ordem:

1. **Antes do primeiro commit, verifique onde está:**
   `git branch --show-current` + `git branch --merged origin/main | grep -Fx "<branch>"`.
   Se a branch atual **já foi mergeada**, NÃO commite nela — crie outra a partir de
   `origin/main`. Branch mergeada está congelada: o PR não reabre, o nome já não descreve
   o novo trabalho e a base está velha (em 08/08 estava 5 commits atrás).
2. **Uma branch por assunto**, nome descrevendo o que ela faz.
3. **Ao encerrar:** commit → push → PR → **merge** → `git branch -d` local e remota.
   Deixar a branch viva depois do merge é o que produziu 14 branches órfãs e 24 worktrees
   mortas até a limpeza de 08/08.
4. **Trabalho em produção via MCP conta como entregue:** migration aplicada e edge
   deployada precisam do arquivo versionado **no mesmo dia**. `apply_migration` e
   `deploy_edge_function` não geram arquivo — versionar à mão e conferir (comparar o md5
   do corpo da função com produção).
5. **Nunca `--force` sem necessidade real.** O único uso legítimo em 08/08 foi remover
   credencial do histórico depois que o gitleaks barrou o CI.

⚠️ **A `main` pode estar presa numa worktree.** O git não permite a mesma branch em dois
lugares; se `git checkout main` falhar com *"already used by worktree"*, é isso. Nesse
caso trabalhe em branch e mergeie ao final — não tente liberar a `main` removendo worktree
alheia sem conferir `git status` dela (em 08/08 a que segurava a `main` tinha 8 arquivos
modificados de outra pessoa).

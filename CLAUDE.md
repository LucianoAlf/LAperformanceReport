## Stack

- **Frontend:** React 19 + TypeScript 5.8 + Vite 6 (porta 5175)
- **Styling:** Tailwind CSS (dark mode via `class`) + Radix UI + Lucide icons + CVA
- **Backend:** Supabase (PostgreSQL + Auth + RLS + Storage + RPC)
- **IA:** OpenAI API (assistente com function calling)
- **Automação:** n8n (webhooks)
- **Routing:** React Router 7 (lazy loading por rota)
- **Forms:** React Hook Form + Zod
- **Charts:** Recharts
- **Datas:** date-fns

O Emusys reenvia o webhook `matricula_renovacao` inteiro a cada edição de cronograma; a `competencia` é calculada e muda entre entregas (antecipada↔normal), então NÃO serve de chave de dedup. `matricula_id` é estável → dedup na edge por `emusys_matricula_id` (janela 60 dias), mantendo o check antigo (aluno+curso+competência) como rede. - **`movimentacoes_admin` não aceita mais DELETE de usuário (2026-08-10).** Trigger `trg_bloqueia_delete_movimentacao_admin` recusa DELETE quando há JWT na sessão; o caminho é a RPC **`arquivar_movimentacao_admin(id, motivo)`**, que move a linha para `movimentacoes_admin_arquivadas` com autor/data/motivo. `service_role` segue livre — a edge precisa apagar aviso prévio removido na fonte. **Por que lixeira e não soft delete:** `anulado` existe e é respeitado por `movimentacoes_admin_vigentes`, mas **25 funções vivas ainda leem a tabela crua** — marcar `anulado` nelas não surtiria efeito, e migrar as 25 é risco desproporcional; mover a linha a some das 25 de uma vez (mesmo padrão de `alunos_arquivados`). Os dois mecanismos coexistem com sentidos distintos: **anulado** = "existe mas não conta" (duplicata de renovação, rastro visível); **arquivado** = "não deveria existir". ⚠️ Motivo do bloqueio: em 03/08/2026 a ADM do Recreio deletou a renovação da Catarina Petrolongo (`audit_log` registro 3178) — via duas linhas da mesma aluna e **a tela só oferecia excluir**. Apagou justamente a do webhook, a única com a data da 1ª aula, e o snapshot de julho ficou apontando para um registro inexistente. Detecção contínua em **`vw_renovacoes_duplicadas_suspeitas`** (já desconta anuladas desde `20260810172458`; é SUSPEITA, não veredito — o padrão `valor_congelado` tem falso positivo por construção).
- **`motivo_saida_id` é resolvido por TRIGGER, não pela edge (2026-08-20).** A tradução do texto do motivo (`movimentacoes_admin.motivo`, que vem do Emusys) para a FK `motivo_saida_id` morava **só** dentro de `processar-matricula-emusys` e rodava **uma vez, no INSERT**. Motivo que não existisse em `motivos_saida` naquele instante gravava NULL, e cadastrar o motivo depois **não retroagia** — medido: 34 evasões com a Pesquisa de Evasão travada em `motivo_nao_catalogado`, e em **11 delas o id já existia** ("Concluído e não vai renovar" foi cadastrado em 05/08; as 5 evasões dele são de 01/08). Hoje quem resolve é `trg_resolver_motivo_saida_movimentacao_admin` (BEFORE INSERT **OR UPDATE OF** `motivo`, `motivo_saida_id`, `tipo`): vale para todo caminho de escrita (webhook, sync, formulário) e corrige linha antiga no próximo toque. Match por `motivos_saida.nome_normalizado` (coluna **gerada**, `upper(trim(nome))`, com UNIQUE) — alcança também texto com espaço sobrando, que o Emusys manda com frequência. ⚠️ **Escopo é `evasao`, `nao_renovacao` e `aviso_previo`**: renovação nunca usou a coluna (0 de 566 linhas) e trancamento tem `motivo_trancamento_id` próprio. ⚠️ **Id já preenchido nunca é sobrescrito** (não passar por cima de decisão humana), então editar só o texto de uma linha já resolvida deixa o id antigo. ⚠️ Motivo sem correspondente **não quebra nada**: fica NULL e vira log `automacao_log.acao='motivo_saida_desconhecido'` — antes morria em silêncio e só aparecia semanas depois como pesquisa travada na tela. ⚠️ `automacao_log.status` só aceita `ok`|`warn`|`erro`; a 1ª versão gravava `'aviso'`, violava o CHECK e caía no `exception when others`, deixando justamente o alerta sem rastro. ⚠️ **Nem todo travado é motivo faltante**: `Contrato concluido sem renovacao` (7) e `Via Emusys (automação)` (3) são rótulos gerados por nós quando **ninguém declarou motivo** — cadastrá-los seria inventar dado.
- **Competência da renovação = mês da 1ª AULA do novo ciclo (regra confirmada pelo Alf, 2026-08-10).** Não é o mês em que a equipe negociou, nem o mês em que o contrato passa a faturar. ⚠️ **Havia duas fontes de escrita com regras diferentes para o mesmo campo**, e era a causa-raiz das duplicatas de renovação: o webhook (`processar-matricula-emusys`) usa `inicioMesISO(dataPrimeiraAulaNovoCiclo || dataMovimento)` ✅, mas o `FormRenovacao` calcula pelo mês da `data_renovacao` ❌ — e o lançamento manual **não tem** a data da 1ª aula. Resultado: a equipe lançava à mão ao negociar, o Emusys mandava o webhook dias depois com a data real, e nasciam **duas linhas com competências diferentes** (medido: 4 casos só no Recreio/jul-2026 — lote manual de 03/07 com 1ª aula real em 03/08, 05/08 e 10/08). A edge agora **reconcilia em vez de ignorar**: ao achar um lançamento adiantado sem 1ª aula, completa a data, recalcula a competência e faz backfill do `emusys_matricula_id` (v81). Tem rede para o órfão **sem vínculo** (mesmo aluno+unidade+**curso**, sem 1ª aula, 60 dias) — sem ela a busca por `emusys_matricula_id` não alcança justamente o registro manual, que é o problema. ⚠️ O `FormRenovacao` **continua gravando a competência pelo mês do lançamento**: quem nunca receber webhook do Emusys fica errado (72 órfãos em 60 dias, 61 deles no Recreio). ⚠️ **O recesso escolar desloca a competência de propósito** — a 1ª aula pós-recesso 19/07–01/08 caiu em agosto, então quem renovou em julho conta em agosto. É esperado, não erro.
- **Renovação duplicada: a prova está no CONTRATO, não no valor (2026-08-10).** O Emusys **abre um `contrato_id` novo a cada renovação**, e as parcelas seguintes apontam para ele — contar, **por matrícula**, os contratos que estreiam no ano dá o número real de renovações. Contar por *aluno* erra: Pérola Madeira tinha 2 registros no mesmo mês, mesmo curso e mesmo valor (a cara de uma duplicata) e eram as matrículas **519 e 520** renovando juntas. ⚠️ O critério por **valor da parcela** parece equivalente e não é: renovação sem reajuste não gera degrau (417→417), juros/multa inflam o `valor_pago` criando degrau falso (367→456,61 era juros), e parcela dividida vira duas linhas na mesma competência (406 + 54). ⚠️ **`valor_original` é valor de TABELA** (todo CG = 447) — só o líquido (`− desconto_fixo − desconto_condicional`) reflete o contratado. Bolsista (mensalidade 0 ou 15) não emite parcela, então nenhum dos dois critérios o alcança. Registro duplicado é **anulado, nunca deletado** (`movimentacoes_admin.anulado`); a leitura canônica é a view `movimentacoes_admin_vigentes`. Método e evidência aluno a aluno: `docs/auditorias/2026-08-10-duplicatas-renovacao-por-contrato.md`.

- **A anamnese é da PESSOA, não da matrícula (2026-09-01, LAPE-19).** `anamneses.aluno_id` aponta para `alunos.id`, que é matrícula — então quem fazia 2+ cursos aparecia como "Anamnese não preenchida" nos demais e seria levado a responder o mesmo formulário de novo (medido: 145 pessoas com 2+ matrículas ativas, 18 já haviam preenchido). Hoje a identidade é o par **`(unidade_id, pessoa_chave)`**, com `pessoa_chave` derivada por trigger e a regra numa fonte única, **`vw_aluno_pessoa_chave`** (+ `fn_pessoa_chave_aluno`, que **lê a view** em vez de reimplementar o `case`). **`aluno_id` mudou de sentido: virou PROCEDÊNCIA** — em qual matrícula a anamnese foi respondida, e é o que alimenta a faixa "respondida na matrícula de Violão" na ficha dos outros cursos (há `COMMENT ON COLUMN` dizendo isso). Leitura canônica = **`get_anamnese_aluno(p_aluno_id)`**, que devolve anamnese vigente + procedência + anteriores; ficha, link público e texto de WhatsApp leem dali — não reimplementar a resolução em consumidor novo, é o padrão que gerou as duplicatas de renovação. ⚠️ **`emusys_student_id` sozinho NÃO identifica pessoa**: 91 ids aparecem em 2+ unidades e os **91 têm nomes diferentes** (colisão entre bases do Emusys) — comparar sempre com `unidade_id` junto. ⚠️ Sem id do Emusys a chave é `local:<aluno_id>` e **não propaga** (3 linhas ativas); deduzir por nome é proibido. ⚠️ **`alunos.anamnese_preenchida` continua existindo como ESPELHO**, mantido por `fn_sincronizar_anamnese_preenchida_pessoa` em **três** gatilhos — anamnese completada, matrícula nova e **`UPDATE OF emusys_student_id`** (este último porque o aluno pode nascer sem id do Emusys e recebê-lo depois pelo sync; trigger só de INSERT deixaria a linha para trás em silêncio, o mesmo bug que `motivo_saida_id` teve até 20/08). Ele existe porque **quatro** consumidores leem sem passar pela ficha: filtro da Lista, Conciliação, `features_churn_alunos_ativos` e o filtro de diagnóstico da própria Lista (que também casava por `aluno_id`). ⚠️ A feature `anamnese_preenchida` do modelo de churn **mudou de semântica** nesta data (213 → 237 linhas com o flag). ⚠️ **`get_anamnese_publica` deixou de expor professor**: ela o resolvia pela linha vinculada, então o professor de Bateria leria o nome do professor de Violão — e a página é aberta por token, não sabe quem está do outro lado. ⚠️ **Nada mudou no aviso ao professor** (decisão do Luciano, 01/09): ampliar o envio para todos os professores da pessoa foi **descartado** porque agosto/26 teve **182 anamneses** contra 11 em junho e 14 em julho — num mutirão desses o professor receberia uma enxurrada. ## Módulo de Agenda (`/app/agenda`, desde 2026-08-02)

Grade do dia por unidade. Fonte é `aulas_emusys` + `aula_alunos_emusys`; leitura pela RPC `get_agenda_dia`, que **agrupa** porque `aulas_emusys` guarda uma linha por aluno em turmas e o Emusys duplica cada slot em `tipo=turma` + `tipo=individual`. **Nenhum cron novo**: reusa `sync-metadados-aulas-15m-u0/u1/u2` (15 min) e `sync-grade-futura-*`. **Nenhuma edge function no caminho de leitura** — a tela chama a RPC direto pelo client Supabase. Fase 2 (pendente): cancelar/reagendar (a API já suporta) e visão Semana.
- ⚠️ **A janela 19/07–01/08/2026 NÃO é buraco de dados — é RECESSO ESCOLAR.** O spec original diagnosticou "deleção/falha de sync" e a tela chegou a exibir um banner de alerta; ambos removidos em 02/08/2026. Provas: **89% dos contratos** vão da aula N (até 18/07) direto para a N+1 (a partir de 03/08), sem salto no contador `nr_da_aula`; **zero FK órfã** em `aluno_presenca`, `aula_alunos_emusys` e `emusys_experimentais_raw` (deleção deixaria rastro); as 3 unidades zeradas de forma idêntica, incompatível com falha de sync (token e cron são **por unidade**); e a semana de reabertura tem **70 experimentais contra 36** de uma semana normal, com 5% das aulas regulares — assinatura de escola fechada com comercial ativo. Não há backfill a fazer: essas aulas nunca existiram no Emusys. ⚠️ **Não há calendário acadêmico no banco** — se alguma métrica tratar recesso como "dado faltando", o denominador fica errado.
- ⚠️ **`tipo` é MODALIDADE contratada, não lotação (corrigido 03/08/2026).** Até então o campo contava contratos no horário (1 = "Individual", 2+ = "Turma") e chamava isso de modalidade — por isso um aluno sozinho numa aula de turma aparecia como "Individual" enquanto o Emusys mostrava "Grupo". A modalidade verdadeira **já estava no banco e nunca tinha sido usada**: `emusys_disciplinas_catalogo.modalidade`, populada pela edge `sync-professor-disciplinas-emusys` (`GET /disciplinas?tipo=turma|individual`). Cobertura 179/179 pelo par (`unidade_id`, `curso_emusys_id`). **Na LA quase tudo é disciplina de turma: 164 das 165 aulas** — e a maioria roda com um aluno só. Descartados antes, todos derivados de contagem: `turma_nome` (preenchido em 171 das 179 "individual" — é o nome do slot), `qtd_alunos` do container (**sempre** igual ao nº de contratos) e `cursos.natureza_operacional`/`capacidade_maxima` (pedagógica/comercial e NULL em todos).
- **Filtro é de LOTAÇÃO, não de modalidade.** Como a modalidade é "turma" em 99%, filtrar por ela devolveria quase tudo ou quase nada. O segmented virou **Sozinho | Com turma** (`FiltrosAgenda.lotacao`, lê `qtd_alunos`); a modalidade continua visível no painel de detalhe. Aula com 0 alunos vinculados **não** é "sozinho" — é vínculo faltando, outro problema.
- **Filtros e período:** busca livre (aluno/professor/turma/sala, sem acento), selects de professor/curso/turma, segmented de lotação (Sozinho|Com turma) e ocultar canceladas — tudo no cliente, sobre o que a RPC já devolve. O período usa o `CompetenciaFilter` compartilhado e sincroniza nos **dois sentidos**: trocar o período salta para dentro dele, e navegar para fora reposiciona o período no mês do dia. Sem isso o topo dizia "Jul/2026" com agosto na tela.
- **Aluno preso na turma antiga — reconciliação por webhook (v2, 2026-08-15).** Quando o aluno troca de turma/curso, a aula antiga **continua existindo no Emusys**; ela só deixa de vir na consulta dele. O que fica errado do nosso lado é o **vínculo** (`aula_alunos_emusys`), não a aula — e como a Agenda lê essa tabela, o aluno aparece numa turma que não é mais dele. O webhook **`matricula_alterada`** dispara a edge **`reconciliar-grade-aluno`** (`verify_jwt=false`, bearer em tempo constante), que lê `GET /aulas?pessoa_id=` **paginado** e chama a RPC **`reconciliar_grade_aluno_v2`**, que faz `delete from aula_alunos_emusys` **apenas da linha daquele aluno**. 4 guardas: foto vazia aborta, janela limitada a ontem+ (⚠️ é `< hoje - 1`, não `< hoje` — a edge manda `dataInicio = ontem` e `< hoje` abortaria 100% das chamadas), slot parcialmente vivo preserva (o Emusys entrega o mesmo horário em 2 linhas, `turma`+`individual`) e **presença lançada por humano preserva** (`aluno_presenca.respondido_por` do PRÓPRIO aluno). Provado na API por janela de DATA e na tela: as 4 aulas do aluno 1452 que a v1 cancelaria seguem `cancelada=false` com `alunos=0`. **Aula vazia é comportamento normal do Emusys** (3 das 126 aulas do Recreio em 17/08, 2,4%). A v1 foi dropada. ⚠️ **Ela nunca funcionou**: gravava `cancelada_origem='sync_ausente_emusys'` numa coluna cuja CHECK só aceitava `('emusys','agenda_secretaria')`, todo cancelamento estourava e o try/catch do webhook engolia — validada em **dry-run**, que não escreve e por isso não pegou. ⚠️ **Reagendamento não passa por aqui e nem precisa**: preserva o `emusys_id` e o upsert move a linha (357 reagendamentos, zero duplicata). ⚠️ O cenário em que o Emusys de fato **apaga** a aula (alteração da data da 1ª aula, `data_primeira_aula` é parâmetro do contrato) **não foi observado nenhuma vez** em 4 dias de webhooks reais — segue coberto pelo soft-cancel diário do `sync-grade-futura-emusys`. ⚠️ Ao cruzar com a API use **`emusys_id`**; `aulas_emusys.id` é chave local. ⚠️ Escopo é só o futuro (decisão do Hugo); o backlog não foi limpo.
- ⚠️ **`professor_presenca` é `'ausente'` por DEFAULT no Emusys** — 100% das aulas *futuras* vêm assim sem ninguém ter faltado (medido: 10.522 futuras, todas 'ausente'). Só exibir depois que a aula terminou (`aulaJaOcorreu`), senão a tela acusa falta de metade do corpo docente todo dia.
- **Decisão humana em `aulas_emusys` é protegida por trigger, não por trava na edge (2026-08-12).** `professor_presenca` é escrita por **quatro** caminhos (`sync-presenca-emusys` nos modos `presenca`/`agenda`/`metadados` + `sync-grade-futura-emusys`), e o modo `metadados` roda **a cada 15 min** cobrindo ontem→+14 dias — como o Emusys manda `'ausente'` por default em aula que não ocorreu, a marcação da secretaria durava um ciclo de cron. Medido em 12/08: **77 de 83 marcações (92,8%) revertidas**. Corrigido com a coluna **`professor_presenca_origem`** (espelha `cancelada_origem`) + trigger **`trg_proteger_decisao_humana_aula`**, que devolve o valor humano em qualquer UPDATE que não declare `set_config('app.escrita_humana_aula','on',true)` — flag que só as RPCs `app_{registrar,remover}_presenca_professor_dia` e `app_marcar_presenca_professor_aula` setam. ⚠️ **A discriminação é por flag de transação, não por conteúdo do UPDATE**: sem ela, a própria secretaria ficaria impedida de corrigir a marcação (presente→ausente seria lido como sobrescrita). ⚠️ **Por que trigger e não trava na edge:** o padrão da edge (`cancelamentosHumanos`) cobre só `sync-presenca-emusys` — `sync-grade-futura-emusys:171` grava `cancelada` **sem** ele, deixando o cancelamento humano com furo latente (não exercitado: zero linhas com `cancelada_origem`). O mesmo trigger fecha esse furo. É o padrão de `trg_proteger_anotacoes_fabio`, que já protegia `anotacoes_fabio` na mesma tabela pelo mesmo motivo. ⚠️ `'ausente'` **com** origem preenchida é decisão humana e fica protegido — é o que distingue "a secretaria marcou ausente" de "o Emusys ainda não lançou".

Pegou `vw_disciplinas_modalidade` em 03/08/2026, e ali era grave: view simples (SELECT de uma tabela, sem join nem agregação) é **auto-atualizável**, e com `security_invoker = false` a escrita executa com os direitos do **dono** — qualquer usuário autenticado poderia INSERT/UPDATE/DELETE em `emusys_disciplinas_catalogo`, que tem RLS sem policy justamente para ninguém escrever. Ao criar view: `revoke all ... from public, anon, authenticated` **e depois** `grant select`. Conferir em `pg_class.relacl` — o correto para view de leitura é `authenticated=r`.
- **Adicionar JOIN em RPC `SECURITY INVOKER` exige que o USUÁRIO tenha acesso à tabela nova.** Quebrou a Agenda em 03/08/2026 (`permission denied for table emusys_disciplinas_catalogo`, 100% dos usuários) — mesma armadilha do `aula_alunos_emusys` em 02/08, repetida porque a validação foi feita como `service_role`, que ignora RLS. Quando a tabela é trancada de propósito (RLS ligado + zero policies), a saída é **não destrancá-la**: expor só o necessário numa view com `security_invoker = false` (ver regra acima sobre a ACL dela). Validar sempre com `set local role authenticated` nos três perfis.
- **Recriar função (DROP+CREATE) reabre EXECUTE para `anon`.** O projeto tem `ALTER DEFAULT PRIVILEGES` no schema `public` concedendo EXECUTE em funções novas a `anon` — então `revoke … from public` **não basta**, precisa de `revoke execute … from anon` nominal. Pegou `get_agenda_dia` em 02/08/2026, **de novo `get_kpis_alunos_canonicos_base_v131` em 04/08/2026**, e **de novo `aplicar_retificacao_relatorio_gerencial_retencao_v1` em 10/08/2026** (3ª vez) — que é `SECURITY DEFINER`, então ficou executável por `anon`. Sempre conferir `select proacl from pg_proc where proname='…'` depois de recriar; a ACL correta para RPC de app é `{postgres=X, authenticated=X, service_role=X}`. ⚠️ **`CREATE OR REPLACE` com lista de PARÂMETROS diferente não substitui — cria um overload novo** e deixa a versão antiga órfã (drope-a explicitamente).
  - ⚠️ **E se o parâmetro novo tiver `DEFAULT`, o órfão não fica só inerte: ele QUEBRA quem chamava a função.** Com `DEFAULT`, a assinatura nova também aceita a lista de argumentos antiga, as duas viram candidatas e o Postgres recusa: `function … is not unique` (`Could not choose a best candidate function`). Caso real em 11/08/2026: `upsert_lead` ganhou `p_data_nascimento date DEFAULT NULL` e o webhook de leads do Emusys (n8n `EB0LibpOJCLhKp7M`, que chama com 10 args) falhou em **100% das execuções por 21h — 22 leads perdidos**, mais o `agente-webhook` das campanhas, que chama a mesma RPC e **não checa o `error`**, parando de criar lead no funil em silêncio. **Ao acrescentar parâmetro a uma RPC com consumidor externo (n8n, edge, PostgREST), dropar a assinatura antiga no MESMO commit** — e conferir `select oid::regprocedure from pg_proc where proname='…'` depois, que deve devolver UMA linha. Post-mortem: `daily-notes/2026-08-12.md`.
  - ⚠️ **Chamada por PostgREST com chaves NOMEADAS (`supabase.rpc`) não sofre a ambiguidade** — resolve pela lista de nomes. Por isso o incidente derrubou só o n8n (SQL posicional) e não o observador, que chama a mesma função com as 11 chaves. Ou seja: **o teste pelo front/edge passa e o webhook quebra** — validar a forma que o consumidor real usa, não só a sua.
- **Retificação mensal (`fechamento_mensal_retificacoes`): encadear, nunca partir do payload original, quando o snapshot já tem outra correção.** O leitor sempre pega a retificação **mais recente** por `created_at` (não faz merge de várias). Uma segunda função de retificação que monta `v_payload_corrigido` a partir de `v_snapshot.payload` (puro) em vez do `payload_corrigido` da retificação já existente **apaga silenciosamente a correção anterior** — a mais nova vence sozinha. Toda função nova de retificação sobre um snapshot que pode já ter outra: `select … from fechamento_mensal_retificacoes where snapshot_id=… and base_payload_hash=… order by created_at desc limit 1`, e usar `coalesce(payload_corrigido, snapshot.payload)` como base. Caso real (10/08/2026): a retificação de renovações do bloco gerencial (`aplicar_retificacao_relatorio_gerencial_retencao_v1`) roda sobre o **mesmo snapshot** que já tinha a retificação de financeiro (`aplicar_retificacao_relatorio_gerencial_financeiro_v1`, 08/08) — sem encadear, teria revertido o financeiro. Guarda de escopo (`RETIFICACAO_..._ESCOPO_EXCEDIDO`) que recalcula campos vizinhos e aborta se algo alheio mudou é o padrão pra pegar isso — mas é só um sinal de alerta, não limite de escrita: confira o que a função de fato `jsonb_set` antes de decidir se dá pra confirmar e seguir (parâmetro `p_confirma_*`) em vez de reescrever a guarda pra sumir com o aviso.
- **RPC de KPI lenta: procure trabalho DUPLICADO antes de otimizar query.** `get_kpis_alunos_canonicos` levava 7.495 ms / 2.653.236 buffers porque `get_kpis_alunos_admin_operacional` (3.900 ms / 1.310.073 buffers) era chamada **duas vezes** com os mesmos argumentos — uma dentro de `get_kpis_alunos_canonicos_base_v131`, outra no wrapper de topo. Corrigido em 04/08/2026 (`20260804230945`): o topo calcula uma vez e repassa via `p_admin jsonb`. **7.495 → 3.966 ms**, com md5 do jsonb idêntico em 8 cenários. A conta de buffers denuncia esse tipo de caso: se `buffers(topo) ≈ buffers(a) + buffers(b)`, há repetição. ⚠️ Ao mexer em função grande, **não transcreva o corpo à mão** — leia `pg_get_functiondef()`, faça `replace()` com guarda (`raise exception` se o trecho não bater) e `execute`. ⚠️ O que ainda sobra ali são dois `LEFT JOIN LATERAL` com `OR` no predicado (`emusys_matriculas_estado_atual` e `aluno_jornada_matricula_disciplina`) que impedem uso de índice; reescrevê-los é o próximo ganho (~3,9 s → ~1 s), mas mexe no desempate que define a `pessoa_key` e **pode mudar contagem de aluno** — exige validação aluno a aluno, não só de totais.
  - **Segundo caso, mesma assinatura (08/08/2026): `get_kpis_turmas_canonicos_v2` (Média/Turma).** Lia `get_carteira_professor_periodo_detalhe_canonico_v1` **duas vezes** — direto no CTE `detalhe` e de novo por dentro de `get_kpis_turmas_canonicos_v1` → `get_carteira_professor_periodo_canonica`, que chama a mesma base com os mesmos argumentos. A aritmética denunciou antes de ler o código: detalhe 86.964 buffers + carteira 87.244 ≈ **172.323 do topo**. Corrigido em `20260808213000` lendo a base uma vez e derivando dela o agregado e as turmas unitárias: **1.626 → 299 ms**, 172.323 → 88.869 buffers (trimestral: 1.114 → 564 ms). Paridade exata em Consolidado/Barra/CG/Recreio/trimestral. ⚠️ **A carteira canônica arredonda `media_alunos_turma` para `numeric(10,2)`, a v1 não** — a v1 recalculava a divisão a partir dos campos crus, e era o valor da v1 que chegava à tela; ao internalizar, copiar a divisão **sem `round`**, senão o número muda. ⚠️ **O sintoma não era "query lenta"**: em cache quente rodava em 1,6 s, longe do `statement_timeout` de 8 s do papel `authenticated`. Eram ~172k buffers (405k no trimestral) para devolver 74 linhas — só rápido porque tudo estava em `shared_buffers`. O `57014` aparecia quando o cache esfriava ou havia concorrência, e a aba de Professores dispara esta RPC **e** `get_kpis_professor_periodo_canonico_v3` em paralelo. **Quando o tempo está bom mas os buffers são absurdos para o nº de linhas, o problema já existe — só ainda não apareceu.**
  - ⚠️ **Nem toda RPC lenta tem trabalho duplicado — e comparar pai com filho SEM AQUECER engana.** Na `get_kpis_professor_periodo_canonico_v3` os buffers fecham em todos os níveis (v2 117.132 + fator 87.964 + saídas 2.418 ≈ 203.309): a base canônica roda **uma vez**, não há o que deduplicar. `get_fator_demanda_professor_periodo_canonico_v1` tem base própria (`aulas_emusys`/`aluno_presenca`/jornada/`alunos`) e **não** passa pela carteira, apesar de custar quase o mesmo (87.964). ⚠️ Medições isoladas sugeriram ~714 ms de CPU sobrando dentro de `get_kpis_professor_periodo_canonico` (1.100 ms contra 386 ms dos componentes somados) — **era artefato de cache**: remedindo com os filhos aquecidos na mesma transação, a função dá **341 ms** e a v3 inteira **704 ms**, não 1.731. Ao decompor pai×filhos, aquecer os filhos primeiro **na mesma transação** — senão a conta de tempo não fecha e se persegue fantasma. A conta de **buffers**, essa, é estável e foi a que apontou a duplicação real da Média/Turma.
  - **Limite de otimização de `get_frequencia_professor_periodo_canonica_v1` — decisão consciente de NÃO mexer (08/08/2026).** Ela custa 222 ms lendo só **5.596 buffers** (32% do tempo da v3 com 2,8% dos buffers). A desproporção vem de `vw_aluno_presenca_semantica_v1`, que tem **window function** (`bool_or(...) OVER (PARTITION BY ap.aula_emusys_id)`): window é **barreira de otimização**, então o `data_aula BETWEEN` da função **não desce** para dentro da view — ela varre e ordena as **50.905** linhas de `aluno_presenca` (+ `aulas_emusys` inteira) e só então descarta **49.053 (96,4%)** pelo filtro de data. ⚠️ **O spill de 4,7 MB NÃO custa tempo**: com `work_mem=24MB` o `temp read/written` some e o tempo fica **224 ms** contra 222 — o SO já absorvia no cache de página. Não subir `work_mem` por isso. O único ganho real (~200 ms) exigiria empurrar o recorte de data para dentro da view, que tem **13 consumidores**, incluindo o Health Score V3 (guardrail: fórmula não muda). Desproporcional para uma RPC que roda em 704 ms contra `statement_timeout` de 8 s. Se um dia virar necessário, o caminho seguro é uma função nova parametrizada por período — não alterar a view compartilhada. A partição é por `aula_emusys_id` e uma aula tem uma data só, então filtrar por data antes da window é semanticamente seguro; falta só provar que não há `aula_emusys_id` com duas `data_aula`.
- **Filtro de unidade: `isAdmin || unidadesPermitidas.length > 1`, e "Consolidado" é SÓ de admin (2026-08-05).** O RBAC (`usuario_perfis`) é a fonte das unidades do usuário, com fallback no legado `usuarios.unidade_id`; exposto por `unidadesPermitidas` no `AuthContext` e consumido por `useUnidadeFiltro`/`AppHeader`. ⚠️ **A cláusula `isAdmin ||` não é redundância:** `get_user_unidade_ids()` filtra `unidade_id is not null` nos dois ramos e os 9 admins têm vínculo **global** (`unidade_id NULL`) — a lista deles vem **vazia**, e sem essa cláusula todo admin perderia o seletor. Além disso `fetchPermissoes` nem busca perfis para admin antigo (`setPerfis([])`). ⚠️ **Consolidado manda `p_unidade_id = null`, e 213 das 246 funções que recebem esse parâmetro são `SECURITY DEFINER`** — RLS não as alcança, elas confiam no argumento. Quem tivesse 2 de 3 unidades e escolhesse Consolidado veria a terceira; por isso não-admin multi-unidade escolhe só entre as unidades dele e `filtroAtivo` nunca é null para ele. **Usuário novo já nasce com vínculo RBAC** via trigger `trg_usuarios_sincroniza_rbac` em `usuarios` (é no banco porque há dois caminhos de escrita: a edge `admin-create-user` e um UPDATE direto); com 2+ vínculos ativos o trigger não toca em nada, para não destruir config multi-unidade feita à mão. Etapas 3-6 da migração (reescrever `is_admin()`, 12 funções, 205 checagens no front, remover `usuarios.perfil`) estão **paradas por decisão** — ver `pendencias.md` item 6.
- **Item de flex tem `min-width: auto` — ele NÃO encolhe abaixo do próprio min-content.** A coluna principal do `AppLayout` (o `flex-1` ao lado da sidebar) estava sem `min-w-0`, então crescia além da viewport sempre que a página tinha conteúdo largo, e o que estivesse mais à direita ficava fora da tela. Sintoma que revelou (03/08/2026): o painel de detalhe da Agenda abria **escondido** depois da borda direita — a timeline não cedia os 296 px dele, a coluna inteira é que esticava. Corrigido com `min-w-0` em [AppLayout.tsx](src/components/App/Layout/AppLayout.tsx). ⚠️ **Sem `overflow-hidden` junto**, de propósito: assim conteúdo genuinamente largo continua transbordando visível (com a barra do documento) em vez de ser cortado em silêncio. Regra: todo `flex-1`/`flex-auto` que contém conteúdo de largura imprevisível precisa de `min-w-0`, e quem resolve a rolagem é o filho largo, com `overflow-x-auto` — 82 arquivos do projeto já fazem isso.
- **`cn()` usa `twMerge`: a ÚLTIMA classe conflitante vence, não a ordem de precedência que a lista sugere.** Condições de estilo que podem ser verdadeiras ao mesmo tempo precisam ser mutuamente exclusivas (senão a "prioridade" pretendida depende da ordem das classes no array, não da regra de negócio). Causou bug real no módulo Agenda: 1 em cada 5 aulas experimentais canceladas/reagendadas renderizava com a cor contradizendo o próprio badge.

## Governança de branch (OBRIGATÓRIO — ler antes do primeiro commit)

**Frente encerrada = merge feito.** Não existe "commitei e deixei o PR aberto para depois".
PR aberto com código já aplicado em produção é risco ativo: o banco fica corrigido e a
`main` fica com o código antigo, então qualquer deploy a partir dela **reverte a correção
sem ninguém perceber** — e o sintoma some, porque o dado continua certo. Aconteceu em
2026-08-08 com o PR #75 (faturamento realizado).

Checklist, na ordem:

1. **Antes do primeiro commit, verifique onde está:**
   `git branch --show-current` + `git branch --merged origin/main | grep -Fx "<branch>"`.
   Se a branch atual **já foi mergeada**, NÃO commite nela — crie outra a partir de
   `origin/main`. Branch mergeada está congelada: o PR não reabre, o nome já não descreve
   o novo trabalho e a base está velha (em 08/08 estava 5 commits atrás).
2. **Uma branch por assunto**, nome descrevendo o que ela faz.
3. **Ao encerrar:** commit → push → PR → **merge** → `git branch -d` local e remota.
   Deixar a branch viva depois do merge é o que produziu 14 branches órfãs e 24 worktrees
   mortas até a limpeza de 08/08.
4. **Trabalho em produção via MCP conta como entregue:** migration aplicada e edge
   deployada precisam do arquivo versionado **no mesmo dia**. `apply_migration` e
   `deploy_edge_function` não geram arquivo — versionar à mão e conferir (comparar o md5
   do corpo da função com produção).
5. **Nunca `--force` sem necessidade real.** O único uso legítimo em 08/08 foi remover
   credencial do histórico depois que o gitleaks barrou o CI.

⚠️ **A `main` pode estar presa numa worktree.** O git não permite a mesma branch em dois
lugares; se `git checkout main` falhar com *"already used by worktree"*, é isso. Nesse
caso trabalhe em branch e mergeie ao final — não tente liberar a `main` removendo worktree
alheia sem conferir `git status` dela (em 08/08 a que segurava a `main` tinha 8 arquivos
modificados de outra pessoa).

### Incidente: quebrei a Agenda e o conserto revelou um buraco pior

A migration acima derrubou a grade para **100% dos usuários** com `permission denied for table emusys_disciplinas_catalogo`. `get_agenda_dia` é SECURITY INVOKER, então o join novo passou a exigir acesso do **usuário** ao catálogo — que tem RLS ligado, zero policies e nenhum grant para `authenticated`, de propósito. Validei como `service_role`, que ignora RLS. **É exatamente a armadilha já registrada no `CLAUDE.md` para `aula_alunos_emusys` em 02/08, repetida um dia depois.**

Conserto sem destrancar o catálogo (`20260803170725`): view `vw_disciplinas_modalidade` com `security_invoker = false`, expondo só id/unidade/nome/modalidade. A view roda com os direitos do dono, então a RPC lê sem que o usuário precise de acesso à tabela.

**E aí o conserto abriu algo pior que o bug original.** A ACL da view nasceu com `authenticated=arwdDxtm` — todos os privilégios — por causa do `ALTER DEFAULT PRIVILEGES` do schema, que eu conhecia para funções e não tinha percebido que vale igual para views. Como a view é simples, ela é **auto-atualizável**, e com `security_invoker = false` a escrita executaria **como dono**: qualquer usuário autenticado poderia INSERT/UPDATE/DELETE no catálogo trancado. Fechado em `20260803170817` com `revoke all` + `grant select`; ACL agora `authenticated=r`.

Validado como deveria ter sido desde o início: 165 aulas nos três perfis (admin, unidade, professor), 164 turma + 1 individual, 100 ms como `authenticated` — mesma faixa dos 95 ms de antes.

Duas regras novas no `CLAUDE.md`: `ALTER DEFAULT PRIVILEGES` pega view também, e adicionar join em RPC SECURITY INVOKER exige acesso do usuário à tabela nova.

### Aplicado (~16h25) — `Authorization` no cron da varredura (camada 1 do risco)

## Fix final do review — fallback de competência do relatório mensal (~19h BRT)

Branch `feat/fallback-competencia-relatorio-mensal`. 6 achados do review final corrigidos.

- **CRITICAL — confirmação abria atrás e congelava o Comercial.** `ModalConfirmacao` é Radix (`z-50`), mas o modal de relatório da `ComercialPage` é um `Modal` caseiro `fixed inset-0 z-[100]`; sem stacking context intermediário, a confirmação ficava sob o backdrop e o `DismissableLayer` do Radix punha `pointer-events:none` no body — página travada, promise nunca resolvia, só `Esc` escapava. No Administrativo não acontecia porque lá o modal externo também é Radix. Corrigido elevando o **próprio `ModalConfirmacao` para `z-[110]`** (é sempre a camada mais alta, por definição) — overlay junto, senão o backdrop fica sob o modal externo. Para isso `dialog.tsx` ganhou prop aditiva `overlayClassName` no `DialogContent`. Conferidos os 6 usos existentes de `ModalConfirmacao`: nenhum regride (maior concorrente do projeto é `z-[200]` dos `SelectContent` de `ModalFichaAluno`, tela que não usa o componente).
- **Fallback só para erro de ausência de fechamento.** Antes, qualquer exceção da RPC virava "fechamento indisponível". Exceções levantadas **no banco** (`pg_get_functiondef`): indisponibilidade é `RELATORIO_ADMIN_MENSAL_FECHADO_INVALIDO` (admin, em `get_relatorio_admin_mensal_rico_base_v1`) e `RELATORIO_MENSAL_FECHADO_INDISPONIVEL` (comercial, em `get_relatorio_mensal_snapshot_base_v1`). Só esses dois entram no ramo de fallback; o resto (hash divergente, fonte inválida, parâmetros, retificação) devolve 500 genérico sem `fallback`. ⚠️ `RELATORIO_ADMIN_MENSAL_FECHADO_INVALIDO` ainda conflaciona "ausente" com "hash divergente" — separar exigiria exceção nova na RPC.
- **Filtro `<= alvo` → `< alvo`.** O `<=` deixava o fallback oferecer **o próprio mês pedido** quando a falha não era de disponibilidade ("julho não fechou, gerar julho?" → mesmo erro).

- **Mensagem de erro útil no lugar de "Edge Function returned a non-2xx status code".** A lib lia o corpo da resposta e jogava fora o `error` — justamente o sintoma que a branch existe para eliminar.
```sql
SELECT p.id FROM professores p
LEFT JOIN professores_unidades pu ON pu.professor_id = p.id AND pu.unidade_id = $3::uuid
WHERE p.ativo = true
  AND ( right(regexp_replace(coalesce(p.telefone_whatsapp,''),'\D','','g'),11)
        = right(regexp_replace(nullif($2,''),'\D','','g'),11)
     OR lower(unaccent(pu.emusys_nome)) = lower(unaccent($1)) )
ORDER BY (right(regexp_replace(coalesce(p.telefone_whatsapp,''),'\D','','g'),11)
        = right(regexp_replace(nullif($2,''),'\D','','g'),11)) DESC NULLS LAST
LIMIT 1;
```

`21971899022`, sem o `55`) — comparação literal falharia em silêncio e cairia sempre no fallback.
